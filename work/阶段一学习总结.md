## 2. Python 环境与密钥管理

项目使用 Python 3.12 虚拟环境：

```bash
source .venv/bin/activate
```

退出环境：

```bash
deactivate
```

模型配置保存在 `src/agent_learning/.env`：

```env
DEEPSEEK_API_KEY=实际密钥
DEEPSEEK_API_URL=模型服务地址
DEEPSEEK_MODEL=模型名称
```

代码显式加载当前模块旁边的 `.env`：

```python
from pathlib import Path

from dotenv import load_dotenv


ENV_PATH = Path(__file__).resolve().parent / ".env"
load_dotenv(ENV_PATH)
```

读取必需配置：

```python
def get_required_env(name: str) -> str:
    value = os.environ.get(name)
    if not value:
        raise RuntimeError(f"{name} 未配置")
    return value
```

安全原则：

- 真实密钥只能放在 `.env` 或系统环境变量中；
- `.env` 必须被 `.gitignore` 忽略；
- 仓库中只能提交不含真实值的 `.env.example`；
- 不在日志、异常信息和截图中输出完整密钥；
- API Key、URL、模型名的变量名要与代码完全一致。

## 3. LLM 客户端

客户端负责：

- 读取模型配置；
- 初始化 SDK；
- 接收消息列表；
- 调用模型；
- 检查并返回回答内容。

基本结构：

```python
class LLMClient:
    def __init__(self, temperature: float = 0.5) -> None:
        api_key = get_required_env("DEEPSEEK_API_KEY")
        base_url = get_required_env("DEEPSEEK_API_URL")
        self.model = get_required_env("DEEPSEEK_MODEL")
        self.temperature = temperature
        self.client = OpenAI(api_key=api_key, base_url=base_url)

    def generate(self, messages: list[dict[str, str]]) -> str:
        response = self.client.chat.completions.create(
            model=self.model,
            temperature=self.temperature,
            messages=messages,
        )

        content = response.choices[0].message.content
        if not content:
            raise RuntimeError("模型没有返回文本内容")

        return content
```

客户端尽量保持无状态。某次会话的历史由会话层保存，避免未来多个用户共享客户端时发生上下文串线。

## 4. 消息协议

每条消息包含 `role` 和 `content`：

```python
{
    "role": "user",
    "content": "请解释 Python 装饰器",
}
```

三个基础角色：

| Role | 作用 |
| --- | --- |
| `system` | 定义角色、行为规则、输出风格和边界 |
| `user` | 用户输入 |
| `assistant` | 模型之前的回答 |

一段完整上下文：

```python
messages = [
    {
        "role": "system",
        "content": "你是一位耐心的 Python 导师。",
    },
    {
        "role": "user",
        "content": "什么是装饰器？",
    },
    {
        "role": "assistant",
        "content": "装饰器用于扩展函数或类的行为……",
    },
    {
        "role": "user",
        "content": "请给出一个例子。",
    },
]
```

消息必须按照发生顺序排列。模型接口本身通常不记住上一轮，客户端要在下一轮重新发送相关历史。

## 5. 多轮对话

基础循环：

```python
history_content.append(
    {"role": "user", "content": user_input}
)

try:
    response = llm.generate(history_content)
except Exception:
    history_content.pop()
    raise

history_content.append(
    {"role": "assistant", "content": response}
)
```

正确顺序：

```text
追加用户消息
  ↓
发送完整相关上下文
  ↓
取得模型回答
  ↓
追加 Assistant 消息
```

退出逻辑要放在模型调用前：

```python
if user_input.lower() in {"/exit", "exit", "quit", "退出"}:
    break
```

这样退出命令不会进入历史，也不会产生一次模型调用。

还应处理：

```python
try:
    user_input = input("用户：").strip()
except (KeyboardInterrupt, EOFError):
    break

if not user_input:
    continue
```

## 6. System Prompt

System Prompt 通常是消息列表第一项，并且一段会话中只保留一份：

```python
messages = [
    {
        "role": "system",
        "content": SYSTEM_PROMPT,
    }
]
```

一个较完整的 System Prompt 可以包含：

```text
角色
+ 服务对象
+ 任务方式
+ 输出要求
+ 行为边界
+ 不确定时的处理方式
```

示例：

```text
你是一位耐心的 Python 编程导师，面向有后端基础的学习者。
先解释核心概念，再给出最小可运行示例。
指出常见错误和验证方法，但不要扩展无关知识。
不确定时明确说明，不要编造信息。
```

学习方法是控制变量：对同一个问题依次使用不同 Prompt，比较正确性、结构、语气和教学效果。

切换 System Prompt 时建议清空旧历史，因为旧回答是在另一套规则下产生的：

```python
messages = [
    {
        "role": "system",
        "content": new_system_prompt,
    }
]
```

## 7. 流式与非流式输出

### 7.1 非流式

```python
response = client.chat.completions.create(
    model=model,
    messages=messages,
)
```

执行过程：

```text
发送请求
→ 等待完整回答
→ 一次性获得并显示文本
```

### 7.2 流式

```python
stream = client.chat.completions.create(
    model=model,
    messages=messages,
    stream=True,
)
```

`stream` 是一个尚未消费完的迭代器，不是已经包含完整回答的数据集合。

```python
content_parts: list[str] = []

for chunk in stream:
    if not chunk.choices:
        continue

    content = chunk.choices[0].delta.content
    if not content:
        continue

    print(content, end="", flush=True)
    content_parts.append(content)

full_content = "".join(content_parts)
```

执行过程：

```text
发送一次请求并保持响应连接
→ 一个 chunk 到达
→ for 循环立即处理
→ 等待下一个 chunk
→ 流结束
→ 拼接完整回答
```

`for chunk in stream` 就是接收循环，不应在外层 `while` 中反复创建请求。

一个 chunk 不保证对应一个字、一个单词或一个 Token。应该忽略空片段，并将有效内容拼接起来。

多轮上下文只保存一次完整回答：

```python
history.append(
    {
        "role": "assistant",
        "content": full_content,
    }
)
```

不要把每个 chunk 分别存成一条 Assistant 消息。

## 8. 耗时与 Token 统计

结构化结果：

```python
from dataclasses import dataclass


@dataclass
class LLMResult:
    content: str
    prompt_tokens: int
    completion_tokens: int
    total_tokens: int
    elapsed_seconds: float
```

计算总耗时：

```python
from time import perf_counter


started_at = perf_counter()
response = client.chat.completions.create(...)
elapsed_seconds = perf_counter() - started_at
```

读取 Token：

```python
usage = response.usage

prompt_tokens = usage.prompt_tokens if usage else 0
completion_tokens = usage.completion_tokens if usage else 0
total_tokens = usage.total_tokens if usage else 0
```

含义：

- `prompt_tokens`：System Prompt、历史消息和本轮问题；
- `completion_tokens`：模型生成的回答；
- `total_tokens`：输入与输出 Token 总量。

多轮对话每次重新发送相关历史，因此 `prompt_tokens` 通常会逐轮增长。

流式调用需要区分：

- TTFT：第一段有效内容出现前的时间；
- Total Time：完整回答结束的时间。

```python
started_at = perf_counter()
first_content_seconds = None

for chunk in stream:
    content = chunk.choices[0].delta.content
    if not content:
        continue

    if first_content_seconds is None:
        first_content_seconds = perf_counter() - started_at

total_seconds = perf_counter() - started_at
```

## 9. 上下文窗口基础

需要区分：

```text
full_history：保存完整历史，用于数据库和页面展示
request_messages：本轮真正发送给模型的上下文
```

最简单的策略是始终保留 System Prompt，并只发送最近 N 轮完整对话：

```python
def build_context(
    full_history: list[dict[str, str]],
    user_input: str,
    max_rounds: int = 2,
) -> list[dict[str, str]]:
    system_messages = full_history[:1]
    conversation_messages = full_history[1:]
    recent_messages = conversation_messages[-max_rounds * 2 :]

    return [
        *system_messages,
        *recent_messages,
        {
            "role": "user",
            "content": user_input,
        },
    ]
```

请求成功后，再将本轮 User 和 Assistant 消息写入 `full_history`。这样失败时不需要回滚完整历史。

只保留最近 N 轮的优点：

- 实现简单；
- Token 范围稳定；
- 延迟和成本更可控。

缺点是模型会忘记被裁剪掉的早期信息。后续需要学习摘要记忆和检索记忆。

## 10. 已遇到的典型问题

### 10.1 环境变量读取失败

原因可能包括：

- `.env` 没有被加载；
- `.env` 路径不正确；
- 代码读取的变量名与文件中的变量名不同；
- 把 `os.environ.get(...)` 写成了普通字符串。

错误：

```python
api_key = "os.environ.get('DEEPSEEK_API_KEY')"
```

正确：

```python
api_key = os.environ.get("DEEPSEEK_API_KEY")
```

### 10.2 客户端参数位置错误

`model` 和 `temperature` 是请求参数，不是客户端初始化参数：

```python
client = OpenAI(api_key=api_key, base_url=base_url)

response = client.chat.completions.create(
    model=model,
    temperature=temperature,
    messages=messages,
)
```

### 10.3 保存了历史但没有发送

只执行：

```python
history.append(...)
```

不代表模型能够看到历史。调用时必须传入完整相关消息：

```python
llm.generate(history)
```

### 10.4 流式回答被重复打印

如果 `generate_stream()` 已经实时打印文本，调用方不应再次打印完整回答。完整文本只用于保存上下文或后续处理。
