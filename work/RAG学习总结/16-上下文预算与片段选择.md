# 第十六节：上下文预算与片段选择

## 1. 本节解决什么问题

检索后补取邻居，资料可能越来越多。不能不加控制地把所有正文放进 messages。这节练习：保持 system 和用户问题不变，在预算内挑选完整资料片段，再为实际发送的资料编号。

打开 [context_budget.py](../../src/agent_learning/module_08_rag/context_budget.py)，只完成 select_context 的三个 TODO。消息格式化、基础消息检查、计数接口、演示与测试已经准备好。

本节纯离线，不发送模型请求；下一节整合完整 RAG，再下一节接为 Agent 工具。不会把每个边界问题继续拆成一节。

## 2. 与以前上下文管理的联系

之前主要删除旧的历史对话；这次选择的是检索出来的资料片段。两者都必须给规则、当前问题和输出预留空间。

对于输入和输出共享上下文总上限的模型，概念上：

```text
可用输入预算 = 上下文总上限 - 预留输出 - 安全余量
```

还需满足模型各自的输入、输出限制。这里传入的 input_budget 是已经预留完毕的输入预算，不是未经扣除的上下文总上限。

本节不硬编码某款模型的上限，也不配置 API 的输出参数；未来真实调用时，实际输出上限必须与预留空间协调。安全余量不能保证一个不准确的计数器一定安全。

## 3. 输入是什么

```python
select_context(query, chunks, input_budget, count_messages)
```

- query：用户问题。
- chunks：已经按 ID 去重的候选片段，保持你传入的优先顺序。
- input_budget：输入允许使用的总量。
- count_messages：接收整组 messages 并返回非负整数的计数函数。

计数函数与预算必须使用相同单位。演示使用 demo_character_count，统计 role 和 content 字符数，不是真实 Token，不含协议序列化开销。

真实 Token 预算需要与实际模型及消息格式匹配的计数方式，不能直接拿“每个字符 0.25 Token”等固定比例保证不超限。这里先把选择算法和计数实现解耦，以便后面替换。

## 4. 输入示例

问题：练习角色住在哪里，喜欢什么？

```text
A：练习角色住在示例地区。
B：很长的背景补充，演示中重复了 100 次。
C：练习角色喜欢阅读。

候选顺序：A、B、C
预算：424 个演示字符单位
```

数字依据当前代码实际计算，若修改 system prompt、问题或来源格式，数字会改变。演示代码动态构造预算，不依赖你记住 424。

## 5. 中间每一步得到什么

先计算无资料基础消息（包含 system、问题、空资料提示），大小是 313。小于预算，可以继续；如果连基础消息都放不下，直接报错，不能删 system 或截断用户问题。

接着按顺序尝试：

| 尝试 | 候选消息包含的资料 | 整组消息大小 | 结果 |
| --- | --- | --- | --- |
| 加 A | A | 364 | 放得下，保留 A |
| 再加 B | A、B | 1615 | 超出 424，跳过 B |
| 再加 C | A、C | 424 | 恰好等于预算，保留 C |

必须计算整组消息，不是只算 chunk['text']：还要包括 system、问题、片段编号、来源和分隔符等格式化内容。每次调用 messages_for_chunks 生成实际候选消息，再交给计数器。

### candidate 是什么

```python
candidate = [*selected, chunk]
```

它创建新列表，把“已经保留的片段”与“当前待尝试的片段”放到一起，但不直接修改 selected。

比如 selected=[A]、当前 chunk=B，则 candidate=[A,B]；发现太长后 selected 仍是 [A]。下次尝试 C，candidate 就是 [A,C]。

这与之前 request_messages = [*content, current_user_message] 的展开语法相同。

## 6. 最终返回什么

以下用片段名作简写，真实字段保存完整字典：

```python
{
    "messages": [system消息字典, user消息字典],
    "selected_chunks": [A的字典, C的字典],
    "omitted_chunks": [B的字典],
    "input_size": 424,
    "input_budget": 424,
    "source_count": 2,
}
```

最终 user 消息里，[1] 对应 A，[2] 对应 C，不保留原候选位置产生的 [3]。后续检查引用必须使用这里的 source_count，而不是扩展前命中数或扩展后候选数。

选好后必须重新生成 messages，再计算 input_size；不能误把最后一次被拒绝的候选消息返回。

## 7. 你要填写的三个 TODO

1. 遍历 chunks，创建 candidate，并组装 candidate_messages。
2. 调用 checked_size 计数。小于等于预算就追加到 selected，否则追加到 omitted 并继续下一段。
3. 循环外按 selected 构造最终消息，返回上述六个字段。这里用 return，不是 raise。

“超出就跳过”不能写成 break，否则长 B 后面较短的 C 没机会加入。也不截断正文，避免改变原片段的含义及来源对应关系。

## 8. 策略边界

- 这是顺序贪心选择，不保证最优组合或最终答案最好。
- 输入顺序决定优先级。上一节的“首次出现顺序”可能把邻居放在命中段前面，因此预算紧张时可能挤掉命中段。实际整合时需要明确优先级，例如优先命中再补邻居，不能默认这一顺序适合所有情况。
- 没片段放得下时，返回空 selected、source_count=0 和基础消息；后续生成流程应按无证据处理，不宣称资料库一定没有答案。
- 计数器必须稳定。本节对预算的保证仅相对于传入的计数器；演示字符计数不能保证真实 API 不超限。
- 不处理多轮历史、tool schema、图片等额外输入。将来新增它们时，必须一起进入真实请求的预算计算。
- 这里选择完整片段，不做摘要、不合并 overlap 重复文字。
