## 3. 函数参数是什么意思

```python
collect_retrieval_results(cases, retrieve, k=3)
```

- cases：问题和人工标注列表，目前还没有实际检索排名。
- retrieve：函数。调用 retrieve(query, k)，返回与 search_top_k 一样的 hits。
- k：本次实际检索并评测的 Top-K。

retrieve 是函数本身，传入它不立即检索。只有循环中执行 retrieve(...) 才发生调用。测试时是假函数，live 时是“问题 Embedding + 本地 search_top_k”。核心代码不需要读取密钥，也不需要关心向量如何生成。

## 4. 你的三个 TODO

1. 创建 results，逐题调用 retrieve(case["query"], k)，得到 hits。
2. 按 hits 原来的排名提取 chunk_id，创建新字典，把 retrieved_chunk_ids 加进去。
3. 循环外返回 results。

每道题的结果应类似：

```python
{
    "case_id": "某道题",
    "query": "问题",
    "expected_chunk_ids": ["A", "B"],  # 原标注不变
    "retrieved_chunk_ids": ["X", "A"],  # 实际返回的顺序，仅示例
}
```

不要用 set 或 sorted 改变返回排名；集合去重是单题指标函数截取前 K 条之后的工作。没有命中就保存空列表，这道题仍参与评测。创建新字典，不直接修改 case。

## 5. 执行顺序与费用

main 的 live 分支会先用空结果的本地替身检查两个练习函数是否已实现；这一步不发请求、不是正式评测结果。然后校验标注版本、读取并校验缓存。

正式执行时，每道题编码一次问题 → 本地检索 → 收集排名；全部完成后调用 evaluate_cases，打印实际排名、命中详情和汇总指标。

- 3 道题正常完成共 3 次 Embedding 请求，可能计费。
- 不重新计算 14 段资料向量，不创建或覆盖缓存，不调用聊天模型。
- 默认不请求；客户端关闭 SDK 自动重试，失败时停止，不伪造部分题目的完整报告。
- 缺少缓存、缓存配置不匹配或资料标注过期会报错，不自动重建。
- 再运行一次 --live 会再编码三个问题；当前未做问题向量缓存。先不要重复 live 比较不同 K。
