## 2. 上下文窗口和输入预算

模型的上下文窗口需要同时容纳输入和输出：

```text
输入 Token + 输出 Token ≤ 上下文窗口
```

因此，本次学习采用的输入预算公式是：

```text
输入预算 = 上下文窗口 - 最大输出 Token - 安全余量
```

例如：

```text
上下文窗口：320 Token
最大输出： 80 Token
安全余量： 20 Token
输入预算：220 Token
```

安全余量用于应对：

- 粗略估算与真实分词结果的误差；
- `role`、消息边界和请求格式的额外开销；
- System Prompt、工具定义和其他隐性输入；
- 输出长度的波动。

`multi_turn_chat.py` 中的 `max_tokens=2048` 直接表示“已经计算好的输入预算”，而不是模型的完整上下文窗口。

## 3. Token 粗略估算

### 3.1 `len(messages)` 和 `len(content)`

```python
len(messages)
```

计算的是消息条数，不是字符数。

```python
len(message["content"])
```

计算的是某条消息内容的字符数，包括中文、英文、数字、空格、标点和换行符等。

例如：

```python
messages = [
    {"role": "system", "content": "你好"},
    {"role": "user", "content": "Hello!"},
]

len(messages)                 # 2，表示两条消息
len(messages[0]["content"])  # 2
len(messages[1]["content"])  # 6
```

### 3.2 本次接入实战使用的估算规则

在 `multi_turn_chat.py` 中，本次练习统一假设：

```text
每个字符 ≈ 0.25 Token
```

实现：

```python
from math import ceil


def calculate_tokens(messages: list[dict[str, str]]) -> int:
    total_tokens = 0

    for message in messages:
        content = message.get("content", "")
        total_tokens += len(content) * 0.25

    return ceil(total_tokens)
```

使用 `ceil()` 向上取整，是为了避免低估：

```python
int(0.75)   # 0，向下截断，不适合容量预算
ceil(0.75)  # 1，更保守
```

### 3.3 两套练习估算规则的差异

当前项目中有两套粗略估算规则：

| 位置 | 估算规则 | 用途 |
| --- | --- | --- |
| `context_window_management.py` | 中文字符 `× 0.6`，其他字符 `× 0.3`，每条消息加 4 | 专门的上下文裁剪练习 |
| `multi_turn_chat.py` | 所有字符统一 `× 0.25` | 本次多轮对话接入练习 |

这些系数都只是练习用的经验值，不能代替模型实际 tokenizer 或 API 返回的 `usage`。后续项目化时应统一为一套估算方法。

## 4. 本次掌握的 Python 列表操作

### 4.1 `pop(1)`

```python
removed_message = messages.pop(1)
```

它会删除并返回列表中下标为 `1` 的元素，也就是第二条消息。

如果要删除完整的 `user + assistant` 轮次，连续两次 `pop(1)` 是可行的：

```python
messages.pop(1)  # 删除旧 user
messages.pop(1)  # 原來的 assistant 前移到下标 1
```

更直观的写法是切片删除：

```python
removed_messages = messages[1:3]
del messages[1:3]
```

删除前必须检查长度和角色，否则可能出现 `IndexError` 或误删当前用户问题。

### 4.2 `extend()`

```python
full_history.extend([
    current_user_message,
    assistant_message,
])
```

`extend()` 会把右侧列表中的元素逐个加入 `full_history`。这里会增加两条独立消息，而不是加入一个嵌套列表。

### 4.3 列表解包 `*content`

```python
request_messages = [
    *content,
    current_user_message,
]
```

它表示：

1. 创建一个新列表；
2. 将 `content` 里的消息逐个放入新列表；
3. 将 `current_user_message` 放到最后。

等价写法：

```python
request_messages = content.copy()
request_messages.append(current_user_message)
```

这种写法不会直接修改原来的 `content` 列表。

## 5. 完整轮次裁剪

一段待发送的标准上下文通常是：

```text
[system, user, assistant, user, assistant, current user]
```

裁剪时的保护规则：

- 第一条 `system` 不删除；
- 最后一条当前 `user` 不删除；
- 从最早的历史 `user + assistant` 开始整轮删除；
- 每删除一轮后重新计算 Token；
- 没有历史可删但仍然超限时抛出 `ContextWindowExceeded`。

完整轮次裁剪可以避免这种无效上下文：

```text
[system, assistant, current user]
```

这个 `assistant` 的问题已经被删掉，模型无法准确理解它为什么出现。

## 6. 完整历史与请求上下文

本次最核心的设计是将会话状态拆成两层：

| 状态 | 作用 | 是否裁剪 |
| --- | --- | --- |
| `full_history` | 保存所有成功的用户问题和模型回答，未来可用于数据库、历史页面和审计 | 否 |
| `content` | 保存下一轮可以发送给模型的近期上下文 | 是 |
| `request_messages` | 本轮临时请求，由近期上下文和当前问题组成 | 是 |

关键代码：

```python
current_user_message = {
    "role": "user",
    "content": user_input,
}

request_messages = [
    *content,
    current_user_message,
]
```

当前用户问题必须先加入 `request_messages`，再进行 Token 计算和裁剪。如果先裁剪旧历史、后加入当前问题，就可能把超长问题直接发给模型。

## 7. 正确的请求和状态更新顺序

最终实现的顺序：

```text
读取并校验 user_input
  ↓
创建 current_user_message
  ↓
创建临时 request_messages
  ↓
将当前问题一起纳入裁剪
  ↓
调用模型
  ↓
创建 assistant_message
  ↓
更新 full_history
  ↓
更新下一轮使用的 content
```

核心代码：

```python
request_messages = [*content, current_user_message]

try:
    request_messages = trim_context(request_messages, max_tokens)
    response = llm.generate(request_messages)
except ContextWindowExceeded as error:
    print(f"上下文超限：{error}")
    continue
except Exception as error:
    print(f"模型调用失败：{error}")
    continue

assistant_message = {
    "role": "assistant",
    "content": response,
}

full_history.extend([
    current_user_message,
    assistant_message,
])

content = [
    *request_messages,
    assistant_message,
]
```

## 8. 失败时的状态处理

如果模型调用永远成功，在调用前或调用后写历史的最终结果是一样的。但真实网络请求可能超时、限流或失败，因此必须定义失败语义。

本次练习选择最简单的策略：

```text
请求成功：同时写入 user + assistant
请求失败：两者都不写入
```

这样可以防止下一轮出现：

```text
system
user：第一个问题
user：重试一次
```

未来将会话保存到数据库时，也可以选择保留失败的用户消息，但需要增加 `pending`、`success` 和 `failed` 等状态，不能把失败请求当成完整对话。

## 9. 边界异常

定义业务异常：

```python
class ContextWindowExceeded(RuntimeError):
    """已经没有历史消息可删，但输入仍然超过预算。"""
```

该异常用于区分：

- 上下文超限；
- 消息角色结构异常；
- 普通的模型调用失败。

判断顺序很重要：

```python
if len(current_history) <= 2:
    raise ContextWindowExceeded(...)

if (
    current_history[1].get("role") != "user"
    or current_history[2].get("role") != "assistant"
):
    raise ContextWindowExceeded(...)
```

必须先检查长度，再访问下标 `1` 和 `2`，否则可能在抛出业务异常前先触发 `IndexError`。

## 11. 已遇到的典型问题

### 11.1 直接删除第一条消息

```python
messages.pop(0)
```

如果第一条是 `system`，会直接丢失整段会话的行为规则。

### 11.2 只删除半轮历史

如果删除旧 `user` 后刚好回到预算内，逐条裁剪会留下孤立的 `assistant`。历史上下文应按完整轮次删除。

### 11.3 误删当前用户问题

当只剩 `system + current user` 时，二者都是受保护消息。如果仍然超限，应抛出异常，而不是继续 `pop(1)`。

### 11.4 当前问题没有参与 Token 计算

错误顺序：

```text
先裁剪旧历史
→ 加入当前问题
→ 调用模型
```

正确顺序：

```text
旧历史 + 当前问题
→ 一起计算和裁剪
→ 调用模型
```

### 11.5 模型失败后污染会话状态

如果在模型调用前直接修改 `content`，失败的用户问题会残留在下一轮上下文中。本次通过临时 `request_messages` 解决该问题。

### 11.6 向下取整导致低估

```python
return int(total_tokens)
```

会把不足 1 Token 的估算直接截断为 0。容量预算应使用 `ceil()` 向上取整。
